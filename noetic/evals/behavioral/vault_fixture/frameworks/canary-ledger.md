## 1. Core Idea
Eliminate in-place state mutations with append-only ledgers and eliminate handler sprawl with 2-level nesting and step_ functions.

## 2. Core Heuristic & Trigger
- **When in modeling transactional entity lifecycles and business workflows** → Prioritize **Append-only transition ledger tables** over _In-place mutable status columns_ because in-place mutation destroys causal history and creates unresolvable data drift during concurrent updates. (Rule: `Reject any schema or migration containing status column updates; declare an event ledger table with monotonic sequence keys`) [Tier 1] [Tags: data-architecture, taste-dogma, fintech] [Anchor: Therefore, our primary and governing invariant is: State is modeled as append-only ledger tables; never use a mutable status column.]
- **When in implementing transactional, asynchronous, or multi-phase request handlers** → Prioritize **Two-level maximum indentation with extracted step_ prefixed functions** over _Inline nested conditionals, multi-level try-catch suites, or nested context managers_ because deep nesting obscures transaction boundaries and dramatically elevates defect rates during failure recovery. (Rule: `Handlers nest at most two levels; a third level must become a named step function prefixed step_`) [Tier 1] [Tags: software-design, taste-dogma, clean-architecture] [Anchor: To establish structural discipline in the application layer, we introduce a strict, enforceable syntactic boundary: Handlers nest at most two levels; a third level must become a named step function prefixed step_.]
- **The Core Question / Razor:** "Can every historical state change be proven by an immutable record without consulting a mutable status column?"
- **Governing Invariant:** State is modeled as append-only ledger tables; never use a mutable status column.

## 3. Mental Moves / Procedures
1. Prohibit mutable status column declarations.
2. Model lifecycle transitions as append-only ledger event rows.
3. Enforce strict AST nesting depth <= 2 on request handlers.
4. Extract third-level logic into top-level helper functions prefixed 'step_'.

## 4. Where to Apply
- **Primary Domain:** data-architecture
### Ontology Primitives
- **Append-Only Ledger Table** (`entity`): An immutable sequence of historical facts and lifecycle transitions.
- **Two-Level Nesting Limit** (`variable`): Maximum syntactic indentation depth allowed in transactional request handlers.
- **step_ Function** (`entity`): An extracted top-level named helper function handling third-level operational logic.

### Trade-Off Matrix
| Tension Dimension | Recommended Choice | Sacrificed | Gained | Boundary Flip Condition |

## 5. Anti-Patterns & Boundaries (When it Breaks)
- **The Hybrid Mutation Trap**: Updating a status column and appending to an event log in the same transaction → Creates dual conflicting sources of truth when asynchronous jobs or direct patches bypass the log (Recovery: Drop the status column entirely; compute current status deterministically from latest ledger entry)
