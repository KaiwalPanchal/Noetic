# Framework: Small Functions

**Source:** Clean Code: A Handbook of Agile Software Craftsmanship — Robert C. Martin (https://www.oreilly.com/library/view/clean-code-a/9780136083238/)  
**Linked Interests:** [[interests#clean-architecture]], [[interests#unit-testability]]  
**Tags:** #framework #code-craftsmanship  
**Admission Score:** 5.0/5.0 (Admission Rubric)  
**The Keyboard Test:** Decomposes complex routines into tiny, well-named helper functions.  

---

## 1. Core Idea
Every function should be tiny (4-8 lines), perform one unambiguous task, and delegate sub-steps.

## 2. Core Heuristic & Trigger
- **When in refactoring module routines and procedural logic** → Prioritize **Aggressive decomposition into tiny functions** over _Consolidated cohesive implementation_ because tiny functions isolate side effects and enable comprehensive unit testing. (Rule: `Keep functions under 10 lines and decompose every sub-operation into a dedicated helper`) [Tier 2] [Tags: software-design] [Anchor: The first rule of functions is that they should be small. The second rule of functions is that they should be smaller than that. Functions should rarely be 20 lines long, and hardly ever 100 lines long.]
- **When in writing conditionals and loop blocks** → Prioritize **Single-line extracted function calls within blocks** over _Multi-line nested inline logic_ because extracted descriptive function names provide self-documenting code clarity. (Rule: `Extract any block inside an if, while, or for statement into a named helper`) [Tier 2] [Tags: software-design, clean-code] [Anchor: Every block within an if, else, while, or for statement should be exactly one line long]
- **The Core Question / Razor:** "Can this function be subdivided into two smaller, more focused functions?"
- **Governing Invariant:** Functions should rarely exceed 10 lines and must operate at a single level of abstraction.

## 3. Mental Moves / Procedures
1. Inspect method line count.
2. Identify multiple levels of abstraction.
3. Extract inner blocks into dedicated helper methods.
4. Verify each helper does exactly one thing.

## 4. Where to Apply
- **Primary Domain:** code-craftsmanship
### Ontology Primitives
- **Function Smallness** (`variable`): The line length and cyclomatic compactness of an execution method.
- **Single Responsibility** (`force`): The requirement that a function does exactly one cohesive operation.

### Trade-Off Matrix
| Tension Dimension | Recommended Choice | Sacrificed | Gained | Boundary Flip Condition |
| :--- | :--- | :--- | :--- | :--- |
| Code Granularity | High decomposition into tiny 5-line functions | Locality of reference when reading a top-to-bottom procedure | Effortless unit test isolation and self-documenting method hierarchies | High-performance inner loops where CPU instruction cache misses and call-stack overhead degrade throughput |

## 5. Anti-Patterns & Boundaries (When it Breaks)
- **Monster Method**: A 150-line method containing validation, SQL queries, HTTP calls, and email formatting → Impossible to test edge cases without triggering accidental network side effects (Recovery: Decompose into a coordinator method calling 5 single-responsibility helpers)
