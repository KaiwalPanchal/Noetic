# Framework: Deep Modules

**Source:** A Philosophy of Software Design — John Ousterhout (https://web.stanford.edu/~ouster/cgi-bin/book.php)  
**Linked Interests:** [[interests#software-simplicity]], [[interests#cognitive-load-reduction]]  
**Tags:** #framework #software-design  
**Admission Score:** 5.0/5.0 (Admission Rubric)  
**The Keyboard Test:** Designs file client libraries with 3-4 public methods instead of sprawling APIs.  

---

## 1. Core Idea
Modules should maximize the depth of functionality hidden behind a small, simple public interface.

## 2. Core Heuristic & Trigger
- **When in designing public interfaces and library boundaries** → Prioritize **Deep modules with minimal public interfaces** over _Shallow modules exposing internal configuration knobs_ because compact interfaces minimize caller cognitive load and allow implementations to evolve independently. (Rule: `Expose at most 3-5 high-leverage public methods hiding internal complexity`) [Tier 2] [Tags: software-design, architecture] [Anchor: A deep module is one whose interface is simple, minimal, and compact, yet the implementation behind that interface provides substantial, powerful functionality.]
- **When in refactoring module routines and procedural logic** → Prioritize **Consolidated cohesive implementation** over _Aggressive decomposition into tiny functions_ because deep modules maximize information hiding and minimize fragmented code navigation. (Rule: `Group related routines into cohesive deep modules rather than shallow helper fragments`) [Tier 2] [Tags: software-design] [Anchor: The best classes and public interfaces are those that do a great deal of work while demanding very little from their callers]
- **The Core Question / Razor:** "Does this interface hide significant complexity, or is it a shallow pass-through wrapper?"
- **Governing Invariant:** Module value equals internal functionality divided by interface surface area.

## 3. Mental Moves / Procedures
1. Examine public method count.
2. Identify internal complexities that can be managed automatically.
3. Condense public interface to core high-leverage verbs.
4. Conceal configuration flags behind robust internal heuristics.

## 4. Where to Apply
- **Primary Domain:** software-design
### Ontology Primitives
- **Deep Module** (`entity`): A module with a simple, compact interface that hides profound internal complexity.
- **Shallow Module** (`entity`): A module whose interface complexity is large compared to the small value it provides.
- **Information Hiding** (`force`): Preventing implementation mechanisms from leaking into client caller scope.

### Trade-Off Matrix
| Tension Dimension | Recommended Choice | Sacrificed | Gained | Boundary Flip Condition |
| :--- | :--- | :--- | :--- | :--- |
| API Exposure | Small public interface with hidden internal mechanisms | Micro-tuning flexibility for callers with esoteric needs | Dramatically lower cognitive overhead and unhindered internal refactoring freedom | Low-level system device drivers where hardware register manipulation must be exposed to callers |

## 5. Anti-Patterns & Boundaries (When it Breaks)
- **Classitis / Shallow Wrappers**: Creating dozens of tiny classes with one 3-line method that simply delegates to another class → Explodes system surface area and forces developers to traverse 15 files to read one operation (Recovery: Consolidate shallow classes into a single deep module with cohesive implementation)
